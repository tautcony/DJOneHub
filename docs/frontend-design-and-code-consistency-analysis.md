# 前端设计与代码一致性分析

## 1. 分析范围

本报告分析 `web/` 前端项目在以下方面的一致性：

- 整体设计语言。
- Ant Design Vue 和自定义组件的使用方式。
- 页面布局、状态反馈和危险操作交互。
- Vue、TypeScript、Pinia、服务层和样式代码的组织方式。
- 自动检查和构建结果。

本报告基于 2026-08-09 的工作区状态。分析以源码和构建结果为依据。本报告不包含真实设备验证和浏览器截图对比。

## 2. 总体结论

前端已有清楚的管理工具设计语言。大部分页面使用相同的导航、页头、面板、表单、按钮和状态颜色。Vue 和 TypeScript 的基础写法也较一致。

当前一致性可以评定为“主干一致，局部漂移”。主要问题不是框架混用，而是共享规则未完全收口：

- 全局样式文件包含大量页面专属样式。
- 设计令牌只覆盖部分颜色和尺寸。
- 多个页面使用不同的状态标记和危险操作确认方式。
- `App.vue` 和 `ViewContext` 承担过多领域职责。
- 格式化规则已配置，但 7 个文件未通过检查。
- 导航能力门控与当前 OpenSpec 规定不一致。
- README 声明的深色和跟随系统外观没有对应的前端实现。

| 维度 | 结论 | 一致性 |
| --- | --- | --- |
| 设计语言 | 浅色工作台、深色侧栏和 Ant Design 语义色形成统一主干 | 较高 |
| 页面结构 | 普通页面较统一，复杂工作台采用独立布局 | 中等偏高 |
| 组件使用 | Ant Design Vue 是唯一基础组件库，共享组件已有有效覆盖 | 较高 |
| 状态和确认交互 | 状态组件、标签、原生状态点和确认框并存 | 中等 |
| 样式组织 | 令牌、全局页面样式和 scoped 样式混合 | 中等偏低 |
| Vue 和 TypeScript | 组合式 API、严格类型和集中服务层较统一 | 较高 |
| 状态管理边界 | 部分领域使用 Pinia，部分领域仍由根组件管理 | 中等 |
| 自动质量门禁 | 类型检查和构建通过，lint 和格式化仍有警告 | 中等 |

## 4. 设计语言分析

### 4.1 已统一的设计主干

前端定位为本地设备管理工具。界面采用高信息密度的工作台结构，没有使用营销页布局。该方向符合产品用途。

基础视觉特征较稳定：

- 固定深色侧栏承载主导航和连接状态。
- 主内容区使用浅灰背景和白色内容表面。
- 蓝色用于主要操作和信息状态。
- 绿色、黄色和红色用于成功、警告和危险状态。
- 页面标题使用统一的 `PageHeader`。
- 常规功能页面使用 `Panel`、表单和紧凑的字段列表。
- 短信、eSIM、固件和运行时诊断使用针对任务设计的工作台布局。

响应式处理覆盖了桌面、平板和窄屏。侧栏、双栏页面、短信工作台、固件页面和 eSIM 页面都有对应断点。

### 4.2 设计令牌未完全收口

`web/src/style.css` 在根节点定义了背景、表面、边框、文本、主色和状态色。该令牌集合提供了基础方向。

但是，页面样式仍直接使用大量颜色值。源码中共有 70 个不同的十六进制颜色。常见 Ant Design 色值和另一组 slate 色值同时存在。例如：

- 通用页面主要使用 `#1677ff`、`#f5f5f5`、`#d9d9d9`。
- 短信页面局部使用 `#f8fafc`、`#475569`、`#172033`。
- 运行时页面局部使用 `#64748b`、`#94a3b8`、`#15803d`。

这些颜色没有映射到统一令牌。新页面很容易继续复制颜色值。

圆角也没有统一尺度。表面容器使用了 6、7、8、9、10、12 和 14 px 等值。头像和药丸标签可以使用特殊圆角，但普通面板缺少明确的尺寸规则。

项目没有使用 Ant Design Vue `ConfigProvider` 来定义主题。CSS 令牌和 Ant Design 组件令牌是两套独立来源。修改主色、圆角或暗色外观时，两个来源可能产生差异。

### 4.3 局部页面形成第二套视觉语言

`RuntimeView.vue` 使用专属图形、节点、抽屉和 slate 色系。该页面的领域需要特殊可视化，因此独立布局合理。但是，标题、状态和表面层级也采用了独立实现。

`SmsView.vue` 使用会话列表、消息气泡和固定编辑器。该工作台结构也符合任务需要。但是，短信存储区域在 scoped 样式中定义了另一组背景和文本颜色。

复杂页面不需要强制使用相同布局。它们仍应复用相同的状态色、标题层级、表面边框和间距令牌。

### 4.4 外观功能与产品说明不一致

README 声明管理页面支持浅色、深色和跟随系统外观。但是，`AppearanceSettings.vue` 只有语言和敏感信息显示设置。源码中也没有应用主题状态、系统主题监听或暗色令牌。

因此，当前实现只能确认浅色界面。项目需要实现声明的外观功能，或修正 README 的支持说明。

## 5. 组件使用分析

### 5.1 基础组件库使用一致

项目只使用 Ant Design Vue 作为常规基础组件库。表单、输入框、选择器、按钮、模态框、抽屉、提示和分页都来自该组件库。

`main.ts` 按父组件注册 27 个 Ant Design Vue 组件。该做法统一了模板写法，也避免了在每个页面重复注册组件。

共享组件已有实际覆盖：

- `Panel` 用于 9 个页面文件。
- `LoadingState` 用于 7 个页面文件。
- `EmptyState` 用于 9 个页面文件。
- `FieldRow` 用于 3 个页面文件。
- `StatusLight` 用于 3 个页面文件，并被 `OperationStatus` 复用。

这些组件的职责小且明确。它们适合作为当前共享层的基础。

### 5.2 状态展示有四种实现

当前状态信息至少使用以下实现：

- `StatusLight`。
- Ant Design `Tag`。
- 固件页面的 `status-dot`。
- eSIM 和 SIM Profile 页面的 `profile-state`。

不同状态需要不同信息密度，但相同语义应使用相同的 tone 映射。当前实现会让 success、warning、danger 和 neutral 在不同页面产生不同颜色、形状和文本结构。

建议保留 `StatusLight` 和 `Tag` 两种层级。项目可以新增统一的状态映射函数。页面不应再定义新的语义色。

### 5.3 危险操作确认方式不一致

eSIM 和 SIM Profile 删除操作使用 Ant Design `Popconfirm`。固件模式切换、USB ID 修改和网络重启使用原生 `window.confirm`。

原生确认框与应用的视觉语言不同。它也不能统一展示风险说明、按钮顺序、加载状态和结构化错误。

建议使用一个共享危险操作确认组件。组件应支持标题、说明、确认按钮文案、危险级别和异步忙碌状态。

### 5.4 页头眉标题

应用页头不再显示“本地控制面”眉标题。页面标题和副标题直接表达当前视图用途，减少技术术语对普通用户造成的干扰。页面内部的 `Panel` 仍可按需要使用眉标题来标识工作区。

### 5.5 组件注册没有解决主入口体积

生产构建的主入口 JavaScript 超过 1 MB。`main.ts` 在应用入口注册所有常用 Ant Design Vue 组件。路由虽然使用动态导入，但共享入口仍包含较多组件代码。

该问题不会直接破坏视觉一致性，但说明当前“按需注册”策略没有实现理想的首屏拆分。项目应使用构建分析确认主入口内容，再决定是否改为页面级组件导入或手动分块。

源码直接导入 `@ant-design/icons-vue`。该包只通过 `ant-design-vue` 间接安装，没有在 `web/package.json` 中直接声明。项目应把直接使用的包声明为直接依赖。

## 6. 代码风格分析

### 6.1 一致的部分

所有 Vue 文件使用组合式 API 和 TypeScript。项目启用了 TypeScript 严格模式。源码中没有发现 `any`、`@ts-ignore` 或 ESLint 禁用注释。

API 请求集中在 `web/src/services/`。页面没有直接使用 `fetch`。设备、SMS、eSIM、网络、SIM Profile 和 VoWiFi 使用 Pinia 管理领域状态。

用户界面文本集中在 `i18n.ts`。界面支持中文和英文。未知操作状态和通话状态使用回退文本。文档语言属性也会跟随当前语言。

错误通知由 `App.vue` 中的统一函数处理。敏感标识符默认遮罩。这些规则在主要页面中保持一致。

### 6.2 根组件职责过重

`App.vue` 有 1533 行。它同时管理以下内容：

- 路由和导航。
- 连接状态和视图刷新调度。
- 通话状态和拨号。
- SMS 操作编排。
- eSIM 操作编排。
- 固件操作和目录选择。
- 原始 AT 状态。
- 通知调试和通知渠道。
- 启动设置和用户偏好。

已有 Pinia store 的领域与仍在根组件中的领域形成两种状态管理方式。新功能无法从现有结构直接判断应该进入 store、页面，还是根组件。

建议让 `App.vue` 只管理应用壳、路由、连接和跨领域事件调度。通话、固件、原始 AT 和设置应使用领域 store 或领域 composable。

### 6.3 `ViewContext` 已成为大型应用接口

`web/src/views/context.ts` 有 257 行。它向所有路由页面暴露大量状态和操作。该接口提供了类型安全，但也把根组件的领域依赖传播到全部页面。

`stores/sms.ts` 还从 `views/context.ts` 导入 `SmsThread` 类型。该依赖使 store 层反向依赖 view 层。

建议把 `SmsThread` 移到 SMS store 或共享类型文件。路由页面应直接使用对应 store。只把真正跨页面的壳层能力保留在小型 context 中。

### 6.4 样式归属规则不一致

`style.css` 有 3803 行。该文件同时包含：

- 全局令牌和基础重置。
- 应用壳和页头。
- 通用面板和状态组件。
- Overview、eSIM、Calls、Firmware 和 SMS 等页面专属样式。
- 多组页面级响应式规则。

同时，Runtime、SMS、Settings 和 Channel Settings 等页面使用 scoped 样式。`RuntimeTraceEdge` 也使用 scoped 样式。

当前代码没有明确规则来决定样式应放在全局文件还是组件文件。全局选择器会增加命名冲突和回归风险。页面删除后，也很难确认对应 CSS 是否可以删除。

建议把令牌、重置、应用壳和共享组件样式保留在全局层。页面专属样式应移动到对应 Vue 文件或页面样式模块。

### 6.5 格式化规则未成为门禁

`npm --prefix web run format:check` 报告以下 7 个文件未通过：

- `CallsView.vue`。
- `FirmwareView.vue`。
- `NetworkView.vue`。
- `OverviewView.vue`。
- `settings/ChannelSettings.vue`。
- `settings/NotificationSettings.vue`。
- `SimProfilesView.vue`。

ESLint 报告 2 个警告：

- `SettingsView.vue` 使用非连字符形式的 `v-model:activeKey`。
- `ChannelSettings.vue` 的 `channelKeys` 只用于类型位置。

类型检查和构建均通过。因此，当前问题主要是规则执行不完整，不是类型安全失效。

### 6.6 前端缺少自动测试

仓库没有已提交的前端单元测试、组件测试或端到端测试。构建可以验证类型和打包，但不能验证以下一致性要求：

- 能力变化后的导航和控制状态。
- 异步操作状态的保留和清理。
- 语言切换和回退文本。
- 危险操作确认。
- 响应式布局和复杂工作台的关键交互。

至少应为能力门控、状态映射和 store 中的纯逻辑增加单元测试。关键路由可增加少量端到端测试。

## 7. 规范偏差

OpenSpec 的 `vue-management-ui` 规范要求隐藏缺少能力的导航项。`App.vue` 当前明确让导航项常驻显示，并把能力缺失交给页面内部处理。

该实现与规范不一致。它也让导航和页面控制采用不同门控规则。项目应先确定产品行为，再同步 OpenSpec 和实现。不要同时保留两种规则。

## 8. 建议优先级

### P0：先消除契约和产品说明冲突

1. 统一能力门控规则。使 `App.vue` 与 OpenSpec 使用同一规则。
2. 实现深色和跟随系统外观，或修正 README 的功能声明。

### P1：建立可执行的一致性基础

1. 让 Prettier 和 ESLint 在持续集成中作为必需检查运行。
2. 把直接使用的 `@ant-design/icons-vue` 加入直接依赖。
3. 定义颜色、圆角、间距和状态 tone 的完整令牌。
4. 让 Ant Design Vue 主题和项目令牌使用同一来源。
5. 统一危险操作确认和状态展示组件。
6. 拆分 `App.vue` 和 `ViewContext` 的领域职责。

### P2：降低后续漂移成本

1. 把页面专属 CSS 移到页面或组件范围。
2. 抽取 Runtime、eSIM 和 Firmware 中可独立维护的区域组件。
3. 增加 store、能力门控和 i18n 回退测试。
4. 分析主入口分块，并降低首屏 JavaScript 体积。
5. 为共享组件记录简短的使用边界和示例。

## 10. 最终判断

前端不是由多套框架拼接而成。它已经形成稳定的 Vue、Pinia、Ant Design Vue 和 i18n 主干。普通管理页面的观感和代码结构较一致。

当前主要风险来自规模增长后的规则分散。设计令牌、样式归属、状态展示、确认交互和领域状态边界都需要收口。完成 P0 和 P1 后，项目可以从“基本一致”提升到“可持续保持一致”。
